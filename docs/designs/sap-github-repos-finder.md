## Problem Statement

SAP developers and consultants need a curated, discoverable list of the most valuable SAP-related GitHub repositories. Currently, finding quality SAP repos means:
- Searching GitHub manually with generic queries
- Sifting through thousands of results with no quality signal
- No structured metadata (SAP area, skills, artifact type, purpose)
- No way to compare repos side-by-side

The existing `fetch_sap_repos.py` script solves the data collection (14 targeted queries, README parsing, SAP area classification, skill extraction, artifact type detection, evidence tracking). Now we need a **reusable app** — a Streamlit web UI with scheduled automation — so users can explore the top 25 SAP repos interactively whenever they need it.

## What Makes This Cool

- **Zero-latency exploration**: Split architecture means the Streamlit UI reads a static `sap_top25.json` from the repo — instant page loads, no API calls on user interaction
- **Weekly freshness for free**: GitHub Action runs the fetch script weekly, commits updated JSON — no server costs, no rate limit worries on page load
- **Rich metadata at a glance**: Each repo shows primary SAP area (10 categories), extracted skills (from topics + README), artifact type (starter template, sample app, SDK, library, tutorial, migration tooling), purpose, and evidence (what matched)
- **Designed for SAP practitioners**: Filters by SAP area, search by skill/keyword, click-through to repo detail with README preview and file tree
- **Portable & deployable**: One-click deploy to Streamlit Cloud with `GITHUB_TOKEN` secret — public URL anyone can use

## Constraints

- **Must use Streamlit Cloud free tier** (no custom backend, no database)
- **Must respect GitHub API rate limits** (5000 req/hr — handled by weekly batch job, not per-user)
- **Must work without local setup** for end users (public URL)
- **Must be maintainable by one person** (simple architecture, minimal deps)
- **fetch_sap_repos.py already exists and works** — don't rewrite, just integrate

## Premises

1. **Static JSON + scheduled refresh beats live API for this use case** — users browse, don't need real-time data; 1-week staleness is acceptable
2. **Streamlit Cloud free tier is sufficient** — no authentication, no database, just static file serving + client-side filtering
3. **14 search queries cover the SAP landscape** — ABAP, OData, Fiori, UI5, Workflow, RAP, CAP, S/4 Conversion, GenAI, Automation
4. **README parsing + keyword matching classifies well enough** — no ML needed for 10 SAP areas
5. **Top 25 by stars is the right signal** — stars correlate with community trust for open source SAP tooling

## Approaches Considered

### Approach A: Live API Mode
Streamlit app calls GitHub API on every page load with caching.
- ✅ Always fresh data
- ❌ Rate limits hit fast on Streamlit Cloud (shared IP)
- ❌ Slow page loads (multiple API calls per repo for README)
- ❌ Can't deploy to free tier reliably

### Approach B: Hybrid (API + Cache)
Streamlit app checks local JSON timestamp; if >7 days old, triggers fetch via GitHub API.
- ✅ Fresher data
- ❌ Still makes API calls on user requests (race conditions, rate limits)
- ❌ Complex state management in Streamlit

### Approach C: Split Architecture (SELECTED)
**GitHub Action runs fetch_sap_repos.py weekly → commits sap_top25.json → Streamlit UI reads static JSON**
- ✅ Zero API calls on page load — instant, free, unlimited users
- ✅ Weekly freshness guaranteed by cron
- ✅ No rate limit exposure for users
- ✅ Simple deployment (just push to GitHub)
- ❌ Data up to 7 days stale (acceptable for browsing)

## Recommended Approach

**Approach C: Split Architecture** — The fetch script runs as a scheduled GitHub Action, commits the updated `sap_top25.json` to the repo. The Streamlit app (`streamlit_app.py`) reads this static file and provides:
- Interactive table with sorting, filtering by SAP area, search by skill/keyword
- Repo detail drill-down (click row → expander with README preview, topics, evidence, link to GitHub)
- CSV/JSON export buttons
- Responsive layout for desktop/mobile

## Open Questions

## Distribution Plan

**Deliverable**: Public Streamlit web app at `https://sap-github-repos.streamlit.app` (or similar)

**CI/CD Pipeline**:
1. Push to `main` branch → GitHub Action `weekly-fetch.yml` runs on schedule (cron: `0 6 * * 1` — Monday 6 AM UTC)
2. Action checks out repo with **PAT** (token: `${{ secrets.PAT }}`), sets up Python, installs `requests`, runs `fetch_sap_repos.py` with `GITHUB_TOKEN` secret
3. If JSON changed, commits and pushes `sap_top25.json` back to repo (triggers Streamlit Cloud redeploy)
4. Streamlit Cloud auto-deploys on push to `main` (reads `streamlit_app.py` and `sap_top25.json`)

**Secrets Required**:
- `PAT` (Personal Access Token with `repo` + `workflow` scopes) — in GitHub Actions secrets (for checkout with write + trigger deploy)
- `GITHUB_TOKEN` (classic PAT with `public_repo` scope) — in GitHub Actions secrets (for fetch script API calls)
- **No secrets needed in Streamlit Cloud** — reads static JSON from repo

**Local Development**:
- `.env.example` with `GITHUB_TOKEN=`
- Run `streamlit run streamlit_app.py` locally

## Error Handling

**Streamlit App** (`streamlit_app.py`):
- If `sap_top25.json` missing: show friendly error with "Run fetch script locally or wait for weekly Action" message
- If JSON corrupted/invalid: show error with "Data file corrupted — check GitHub Action logs" and link to Action run
- If JSON empty: show "No repositories found — check GitHub Action" with timestamp of last successful run

**GitHub Action** (`weekly-fetch.yml`):
- Uses built-in `GITHUB_TOKEN` (auto-available, has `contents: write`)
- `continue-on-error: false` (default) — failed runs show red in Actions tab
- Optional: add Slack/email notification on failure via `actions/github-script` or `if: failure()` step
- Retries: script has exponential backoff (5 retries, base 2s) for rate limits and 5xx errors

## Testing Strategy

3. **Action test**: Push to `test` branch → Action runs → verify `sap_top25.json` committed
4. **Smoke test**: Deploy to Streamlit Cloud staging → verify public URL loads, filters work, exports download
5. **Regression**: After any change to `fetch_sap_repos.py`, run local fetch + UI test

## Evidence Display Format

In repo detail expander, "evidence" shows as:
- **Matched Topics**: Badge chips (e.g., `abap`, `sap`, `cds`) — from `evidence.matched_topics`
- **Matched Keywords**: Badge chips with area prefix (e.g., `ABAP:cds`, `Fiori:fiori elements`) — from `evidence.matched_keywords`
- **Matched Queries**: Small text list (e.g., "topic:abap fork:false sort:stars") — from `evidence.matched_queries`
- **README Used**: Yes/No indicator — from `evidence.readme_snippet_used`

## Artifact Type Classification Logic

From `summarize_readme()` (line 291-347): Scans README content (lowercased) for keyword indicators in order:
1. starter template: "starter", "template", "boilerplate", "scaffold"
2. sample app: "sample", "example", "demo", "reference implementation"
3. SDK: "sdk", "client library", "client sdk"
4. library: "library", "package", "module", "utility"
5. tutorial: "tutorial", "workshop", "guide", "learning", "exercise"
6. automation scripts: "script", "automation", "cli tool", "migration tool"
7. migration tooling: "migration", "conversion", "transformation", "upgrade"
First match wins; default "project" if none.
